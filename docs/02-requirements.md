# 2. Вимоги до системи

## 2.1 Ролі

| Роль | Код | Клієнт системи | Тип |
|---|---|---|---|
| Клієнт | `CLIENT` | Mobile (основний), Web | бізнес-роль |
| Працівник залу (хостес / офіціант) | `STAFF` | Web, Mobile | бізнес-роль |
| Кухар | `KITCHEN` | Web, Mobile (Kitchen display) | бізнес-роль |
| Адміністратор | `ADMIN` | Web, Mobile (аналітика, користувачі) | технічна роль (+ усі права персоналу) |

Ролі відрізняються операціями, правами, сценаріями й доступними даними; усі перевірки виконуються **на сервері** (RBAC у кожному endpoint + права переходів у скінченних автоматах).

## 2.3 Нефункціональні вимоги

| Категорія | Вимога | Як перевіряється |
|---|---|---|
| Продуктивність | API відповідає < 300 мс на типових запитах при 50 столиках / 5000 замовлень | тест швидкодії, `/api/health` показує затримку БД |
| Продуктивність | Real-time подія доходить до клієнта < 1 с | інтеграційний тест Socket.IO |
| Надійність | Неможливо створити два активні бронювання столика з перетином (навіть при гонці запитів) | advisory lock + EXCLUDE-обмеження, тест «в обхід API» |
| Надійність | Неможлива подвійна оплата | блокування рядка `FOR UPDATE`, partial unique index, `Idempotency-Key` |
| Безпека | Паролі — bcrypt; JWT 30 хв; refresh-токени зберігаються як SHA-256, одноразові, з виявленням повторного використання | автотести TC-05 |
| Безпека | RBAC на сервері, приховування кнопок у UI не є авторизацією | автотести TC-07 |
| Безпека | Серверна валідація всіх вхідних даних (zod), єдиний формат помилок | автотести TC-03 |
| Безпека | Номер картки не зберігається (лише бренд і last4) | тест TC-15 |
| Безпека | Rate-limit на вхід/реєстрацію (20/хв), helmet, CORS | конфігурація |
| Usability | Mobile-first UI, темна тема, тактильний відгук, сповіщення | демонстрація |
| Адаптивність | Web коректно працює від 360 px до 1920 px | скриншоти |
| Сумісність | Web: Chrome/Firefox/Safari/Edge (2 останні версії); Mobile: iOS 16+/Android 10+ (Expo SDK 57) | |
| Масштабованість | Stateless API (JWT) — можна запускати кілька інстансів за балансувальником | архітектура |
| Збереження даних | PostgreSQL, міграції Prisma, обмеження CHECK/FK/UNIQUE/EXCLUDE, журнал змін статусів | `prisma/migrations` |
| Оброблення помилок | Людські повідомлення українською з кодом помилки; альтернативи при конфлікті бронювання | автотести |

## 2.5 CORE / ADVANCED / BONUS

| Рівень | Реалізовано |
|---|---|
| **CORE** | Web, Mobile, Backend/API, єдина БД PostgreSQL, 4 ролі, JWT + RBAC, меню, столи, бронювання, замовлення, статуси, Web/Mobile-інтеграція, автотести |
| **ADVANCED** | Booking engine (слоти, best-fit, фрагментація, альтернативи, EXCLUDE), QR (бронювання, столики, walk-in, сканер у Web і Mobile), sandbox payment (Luhn, 3-D Secure, ідемпотентність, чайові, готівка) |
| **BONUS** | Kitchen display, рекомендації (асоціативні правила + персоналізація + байєс), real-time (Socket.IO), прогноз ETA, аналітика, Docker, CI, Swagger, 77 автотестів + E2E, стоп-лист, журнал змін статусів |
