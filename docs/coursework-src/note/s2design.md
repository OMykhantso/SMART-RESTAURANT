### 2.1 Проєктування архітектури та взаємодії компонентів системи

Система складається з двох незалежних серверних систем, які працюють з однією базою даних (рис. 2.1). Клієнти ніколи не звертаються до бази даних напряму: Web і Mobile надсилають запити до API, API виконує бізнес-логіку і працює з PostgreSQL. Так реалізовано базову архітектуру «Web/Mobile → API → Backend → Database».

!fig 2.1 | ../../diagrams/architecture.png | Діаграма архітектури системи Smart Restaurant

Призначення компонентів:

- **Web-застосунок** — сайт гостя (меню, бронювання, кабінет, оплата) і робочі місця персоналу, кухні та адміністратора; працює з Restaurant API.
- **Mobile-застосунок** — застосунок гостя (зал і доставка), курʼєра та персоналу; працює з обома системами.
- **Restaurant API (порт 4000)** — меню, столики, бронювання, check-in, замовлення в залі, kitchen display, оплата, відгуки, аналітика, користувачі.
- **Delivery API (порт 4100)** — зони, геолокація, адреси, оформлення й оплата доставки, черга курʼєрів, диспетчерська, статуси доставки.
- **Спільне доменне ядро** — схема бази даних, автомат станів замовлення, перевірка JWT, модуль оплат. Обидві системи використовують одні правила, тому статуси не розходяться.
- **Real-time (Socket.IO)** — кожна система надсилає події своїм клієнтам у кімнати користувача, залу, кухні та курʼєрів.
- **Фонові задачі** — Restaurant API скасовує непідтверджені бронювання і позначає no-show; Delivery API скасовує неоплачені доставки через 15 хв.
- **PostgreSQL** — єдина база даних для обох систем; цілісність гарантують обмеження CHECK, FK, UNIQUE, EXCLUDE і тригер.
- **Платіжний шлюз (sandbox)** — зовнішній сервіс, емульований у коді: перевірка картки, 3-D Secure, відмови, повернення коштів.

**Як дві системи працюють з однією базою даних.** Кожна система записує зміни у спільні таблиці у власній транзакції. Після успішного запису вона надсилає подію через механізм PostgreSQL LISTEN/NOTIFY [8] (канал sr_orders). Друга система слухає цей канал, читає актуальний стан замовлення з бази даних і сповіщає своїх клієнтів. Приклад:

1. Клієнт оформлює й оплачує доставку в мобільному застосунку — Delivery API створює замовлення типу DELIVERY.
2. PostgreSQL передає подію в Restaurant API — кухар одразу бачить тікет із позначкою «Доставка» на Web або Mobile.
3. Кухар позначає «Готово» в Restaurant API — подія повертається в Delivery API, курʼєр отримує сигнал «можна забирати».
4. Курʼєр забирає й доставляє замовлення — клієнт бачить статус «В дорозі», а потім «Доставлено».

Так Web-застосунок лишається без змін, а доставка працює як окрема система, яку можна запускати, оновлювати й масштабувати незалежно. Обидві системи приймають той самий JWT: користувач входить один раз через Restaurant API.

### 2.2 Проєктування бази даних

Логічна модель бази даних (рис. 2.2) побудована навколо замовлення (orders). Замовлення в залі привʼязане до бронювання-візиту і столика, а замовлення на доставку — до запису доставки з адресою, зоною та курʼєром. Тип замовлення (DINE_IN або DELIVERY) зберігається в самій таблиці orders, тому кухня, оплати, відгуки й аналітика працюють однаково для обох типів. Схема нормалізована до 3НФ, містить 14 таблиць і реалізована в PostgreSQL 16 через міграції Prisma ORM; обмеження, які не виражаються засобами ORM (EXCLUDE, часткові унікальні індекси, CHECK, тригер), додано окремими SQL-блоками в міграціях.

!fig 2.2 | ../../diagrams/er-diagram.png | Логічна модель бази даних

На діаграмі показано первинні (PK), зовнішні (FK) та унікальні (UK) ключі й кардинальність звʼязків. Для читабельності не намальовано допоміжні звʼязки: users → addresses, users → deliveries (courier_id), users → reviews, tables → orders, dishes → reviews та orders → status_changes.

Таблиці за призначенням:

- **Спільні:** users (облікові записи всіх пʼяти ролей), refresh_tokens (сесії), categories і dishes (меню), orders і order_items (замовлення залу й доставки), payments (оплати та повернення), reviews (відгуки), status_changes (журнал змін статусів).
- **Зал (Restaurant API):** tables (столики й план залу, QR-токени), reservations (бронювання-візит: гість, столик, інтервал часу, статус).
- **Доставка (Delivery API):** delivery_zones (зони з тарифами, центром і радіусом для геолокації), addresses (адреси клієнтів), deliveries (доставка замовлення: отримувач, телефон, знімок адреси, курʼєр, тариф, час виїзду і вручення).

Найважливіші обмеження цілісності:

- **reservations_no_overlap** (EXCLUDE): один столик неможливо забронювати двічі на час, що перетинається, навіть при одночасних запитах;
- **payments_one_success_per_order** (частковий UNIQUE) та **idempotency_key** (UNIQUE): замовлення не може бути оплачене двічі;
- **orders_type_consistency** (CHECK): замовлення в залі завжди має бронювання і столик, а доставка — ні;
- **deliveries_order_type** (тригер): запис доставки можна створити лише для замовлення типу DELIVERY;
- **deliveries_phone_format, deliveries_change_only_cash, deliveries_timeline_order** (CHECK): телефон у форматі +380XXXXXXXXX, решта лише для готівки, час вручення не раніше часу виїзду;
- **addresses_one_default_per_user** (частковий UNIQUE): у клієнта лише одна адреса за замовчуванням;
- **delivery_zones_center_pair, delivery_zones_radius_range** (CHECK): центр зони задається обома координатами, радіус — від 0,5 до 50 км;
- **CHECK для сум і кількостей:** ціни, тарифи, кількість і суми лише в допустимих межах; гроші зберігаються в копійках.

Для частих запитів створено індекси: бронювання столика за часом, замовлення за статусом і датою (зокрема складений індекс type, status, created_at для черги кухні й диспетчерської), доставки за курʼєром і зоною, адреси за користувачем.
