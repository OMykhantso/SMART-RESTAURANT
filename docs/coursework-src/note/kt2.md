## АНОТАЦІЯ

Звіт до контрольної точки № 2 курсової роботи «Інтернет-проєкт» підтверджує, що система SMART RESTAURANT на цьому етапі є працездатним комплексом Web + Backend/API + база даних, а не набором макетів.

Фізично створено базу даних PostgreSQL із 14 таблиць через міграції, реалізовано Restaurant API з автентифікацією, авторизацією за ролями, серверною валідацією, основними сутностями та бізнес-логікою станів, а також Web-застосунок для гостя, працівника залу, кухаря й адміністратора. Дані реально зберігаються в базі даних, вихідний код ведеться в Git-репозиторії.

У звіті описано архітектуру й логічну модель бази даних, інтерфейси, реалізацію Backend і API, а також результати перевірки автентифікації, ролей, валідації та основного бізнес-процесу.

## ВСТУП

Темою курсової роботи є інформаційна система ресторану **SMART RESTAURANT** з онлайн-бронюванням, QR check-in, замовленням зі смартфона, оплатою та доставкою. Аналіз і проєктування погоджено на контрольній точці № 1.

Згідно з методичними вказівками на КТ № 2 потрібно продемонструвати фізично створену базу даних, Backend, API, автентифікацію, авторизацію, ролі, серверну валідацію, основні сутності, основну бізнес-логіку, працездатний Web, реальне збереження даних і Git-репозиторій. Де саме виконано кожну вимогу:

- фізично створена база даних, основні сутності – підрозділ 2.2, міграції Prisma в `backend/prisma/migrations`, команда `npm run db:setup`;
- Backend і API, документація API – підрозділ 2.4, Swagger UI `/api/docs` (59 endpoint Restaurant API);
- автентифікація, авторизація, ролі, серверна валідація – підрозділ 2.4, тести TC-01, TC-03, TC-05, TC-07 (табл. 3.1);
- основна бізнес-логіка – автомати станів бронювання й замовлення (рис. 2.10), тести TC-11…TC-26 (табл. 3.1);
- працездатний Web і реальне збереження даних – підрозділ 2.3 (рис. 2.3–2.5) і розділ 3;
- Git-репозиторій – https://github.com/OMykhantso/SMART-RESTAURANT, історія змін і безперервна інтеграція GitHub Actions.

## РОЗДІЛ 3. ПЕРЕВІРКА ПРАЦЕЗДАТНОСТІ

Працездатність комплексу Web + Backend/API + база даних перевірено автоматизованими інтеграційними тестами на реальній PostgreSQL в окремій тестовій базі даних і вручну через Web-застосунок. Тести надсилають справжні HTTP-запити до Restaurant API, тому перевіряють одночасно маршрути, валідацію, права ролей, бізнес-правила й обмеження бази даних. Основні сценарії наведено в табл. 3.1.

@include t31.md

Перевірку через Web виконано за сценарієм демонстрації: працівник залу входить у систему, бачить нове бронювання гостя і підтверджує його; гість оформлює замовлення за столиком, офіціант приймає його, кухар готує на kitchen display, офіціант подає страви й фіксує оплату. Після перезавантаження сторінки всі зміни зберігаються, а в таблиці status_changes видно історію переходів зі зазначенням того, хто й коли змінив статус.

Спроби недозволених операцій відхиляє сервер, а не лише інтерфейс: клієнт отримує 403 при спробі підтвердити власне бронювання, офіціант – при спробі перевести замовлення в «Готується», а некоректні дані (пароль «123», бронювання на 08:00) повертають 400 або 422 з поясненням під відповідним полем форми.
