### 2.5 Реалізація Web- та Mobile-застосунків та їх інтеграція

**Web-застосунок** написано на React 19 [10] з React Router 7 і Tailwind CSS. Дані з API завантажуються через TanStack Query [14]: кешування, повторні запити й автоматичне оновлення після подій реального часу. Кожна вкладка браузера має власну сесію (sessionStorage), тому в сусідніх вкладках можна одночасно працювати гостем, офіціантом і кухарем. Події Socket.IO позначають відповідні дані в кеші застарілими (їх одразу завантажено повторно) і показують сповіщення зі звуком: нове бронювання — бейдж у меню і toast, нове замовлення — тікет на kitchen display і в kanban (рис. 2.11). Сканер QR у Web працює через камеру браузера (getUserMedia і бібліотеку jsQR) або фото.

!fig 2.11 | fig/web-orders.jpg | Web: kanban замовлень офіціанта з позначкою «Доставка» для замовлень Delivery API

**Mobile-застосунок** — нативний застосунок на React Native з Expo SDK 57 [11], не WebView. Навігація — React Navigation 7 [15] із власним набором вкладок для кожної ролі. Застосунок працює з двома API через два HTTP-клієнти й два Socket.IO-зʼєднання; адреси обох систем визначаються автоматично або налаштовуються в профілі. Мобільні можливості: expo-camera (QR), expo-location (GPS і геокодер), expo-notifications (локальні сповіщення), expo-haptics (вібрація), expo-secure-store (токени).

**Двостороння інтеграція Web і Mobile.** Обидва клієнти працюють з тими самими endpoint і тією самою базою даних, а сервер сповіщає зацікавлені сторони через кімнати Socket.IO: user:<id> — конкретний користувач, staff — зал, kitchen — кухня, couriers і dispatch — служба доставки.

Сценарій Mobile → Backend/API → Database → Web:

1. Гість у мобільному застосунку створює бронювання (`POST /api/reservations`).
2. Restaurant API перевіряє правила, записує бронювання зі статусом PENDING у таблицю reservations і надсилає подію reservation:created у кімнату staff.
3. У Web працівника залу без перезавантаження сторінки зʼявляється нове бронювання зі звуковим сигналом і бейджем.

Сценарій Web → Backend/API → Database → Mobile:

1. Працівник залу у Web натискає «Підтвердити» (`PATCH /api/reservations/:id/status`).
2. Сервер перевіряє роль і допустимість переходу, оновлює статус і журнал змін, надсилає подію reservation:updated у кімнату user:<id> гостя.
3. На телефоні гостя зʼявляється сповіщення «Бронювання підтверджено!», вібрація, статус на екрані змінюється сам.

Так само проходить замовлення: гість замовляє з телефона, офіціант приймає його у Web, кухар готує на kitchen display, а гість бачить статуси «Готується» і «Готово» з прогнозом часу; після оплати в Mobile офіціант отримує подію про оплату у Web. Для доставки ланцюжок проходить через дві системи: після оплати в Delivery API подія через PostgreSQL потрапляє в Restaurant API, на kitchen display зʼявляється тікет «Доставка», а коли кухар позначає «Готово», подія повертається в Delivery API і сповіщення отримують курʼєр і клієнт.
