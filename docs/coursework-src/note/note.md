## АНОТАЦІЯ

У курсовій роботі розроблено інформаційну систему ресторану SMART RESTAURANT, яка вирішує проблему розірваних процесів обслуговування: бронювання телефоном, черги на вході, очікування офіціанта й рахунку, паперові чеки на кухні та залежність від сторонніх агрегаторів доставки.

Користувачі системи — гості ресторану, працівники залу, кухарі, курʼєри та адміністратор. Система складається з Web-застосунку (React), нативного мобільного застосунку (React Native, Expo), двох серверних систем — Restaurant API і Delivery API (Node.js, Express) — та єдиної бази даних PostgreSQL. Обидва API приймають один обліковий запис, а про зміни спільних замовлень повідомляють одне одного через механізм PostgreSQL LISTEN/NOTIFY.

Реалізовано онлайн-бронювання з booking engine, check-in за QR-кодом, замовлення зі смартфона, kitchen display, sandbox-оплату з 3-D Secure, відгуки й рекомендації, аналітику, а також власну службу доставки з зонами, геолокацією, курʼєрами й диспетчерською. Статуси змінюються в реальному часі на Web і Mobile. Якість підтверджено 118 автоматизованими тестами API, наскрізними тестами в браузері та безперервною інтеграцією.

У першому розділі проведено аналіз предметної області й аналогів, сформовано вимоги та виконано постановку задачі. Другий розділ присвячено проєктуванню архітектури, бази даних, інтерфейсів і програмній реалізації системи. У третьому розділі описано тестування та проаналізовано результати.

## ВСТУП

**Актуальність теми.** Ресторанний бізнес дедалі більше переходить у цифровий формат: гості звикли бронювати столик зі смартфона, бачити меню до приходу, замовляти й платити без очікування офіціанта, а також замовляти улюблені страви додому. Водночас у більшості закладів ці процеси досі розірвані між телефоном, паперовими чеками, окремим POS-терміналом і сторонніми агрегаторами доставки, які беруть комісію й залишають ресторан без даних про клієнтів.

**Проблема.** Через ручне ведення бронювань трапляються подвійні бронювання, на вході утворюються черги, у години пік гості довго чекають на офіціанта й рахунок, кухня губить позиції з паперових чеків, а гість не знає, коли буде готова страва. Доставка через агрегатор не повʼязана з кухнею ресторану і не дає контролю над часом.

**Мета роботи** — автоматизувати повний бізнес-процес ресторану від бронювання до оплати, обʼєднати гостя, зал, кухню і курʼєрів в одну систему реального часу та дати гостю можливість замовити доставку в мобільному застосунку.

Для досягнення мети поставлено такі завдання:

1. Проаналізувати предметну область і аналоги, визначити користувачів та їхні потреби.
2. Сформувати функціональні й нефункціональні вимоги, побудувати модель варіантів використання.
3. Спроєктувати архітектуру, логічну модель бази даних та інтерфейси Web і Mobile.
4. Реалізувати базу даних, Restaurant API і Delivery API з автентифікацією, авторизацією, валідацією та бізнес-логікою станів.
5. Реалізувати Web- і Mobile-застосунки та їхню двосторонню інтеграцію в реальному часі.
6. Реалізувати компоненти підвищеної складності: booking engine, QR, sandbox payment, kitchen display, рекомендації, службу доставки з геолокацією.
7. Протестувати систему і проаналізувати результати.

**Обʼєкт розробки** — процеси обслуговування гостей ресторану в залі та доставки замовлень. **Предмет розробки** — клієнт-серверна інформаційна система з Web- і Mobile-клієнтами, двома серверними системами та єдиною базою даних.

**Практичне значення.** Система готова до використання в реальному закладі: гості бронюють і замовляють без дзвінків і очікування, персонал бачить зал і кухню в реальному часі, кухня працює без паперових чеків, а ресторан отримує власний канал доставки без комісії агрегатора й аналітику за обома каналами продажів.

### 2.4 Реалізація Backend, API та бізнес-логіки

**Структура серверної частини.** Обидві системи — це Node.js-процеси з одного кодового пакета `backend`. Спільне доменне ядро (`lib/`) містить автомати станів, декларативний маршрутизатор, обробку помилок, JWT, роботу з часом і шину подій. Модулі Restaurant API (`modules/`): auth, users, menu, tables, booking, reservations, orders, payments, reviews, recommendations, analytics, uploads. Delivery API (`delivery/`) має власні маршрути, сервіс, Socket.IO, фонові задачі й геолокацію, але використовує той самий модуль замовлень і оплат.

**API.** Restaurant API надає 59 endpoint, Delivery API — 27. Кожен маршрут описано декларативно (лістинг А.3): метод, шлях, опис, ролі, схеми zod для тіла, query- і path-параметрів. З того самого опису генерується специфікація OpenAPI 3.1 [11] і Swagger UI (`/api/docs`), тому документація завжди відповідає коду. Приклади ключових endpoint:

- `POST /api/auth/login` — вхід, повертає access- і refresh-токени (публічний);
- `GET /api/booking/availability?date&guests` — вільні слоти з рекомендованим столиком (публічний);
- `POST /api/reservations` — створення бронювання (CLIENT, STAFF, ADMIN; 201, 409 з альтернативами, 422);
- `PATCH /api/reservations/:id/status` — зміна статусу за автоматом станів (403 TRANSITION_FORBIDDEN, 409 INVALID_TRANSITION);
- `POST /api/reservations/scan-table` — check-in гостя за QR столика (CLIENT);
- `POST /api/orders`, `GET /api/kitchen/orders`, `PATCH /api/kitchen/orders/:id/items/:itemId` — замовлення і kitchen display;
- `POST /api/payments/card`, `POST /api/payments/:id/confirm` — оплата карткою і 3-D Secure (заголовок Idempotency-Key);
- `POST :4100/api/delivery/locate`, `POST :4100/api/delivery/quote`, `POST :4100/api/delivery/orders` — геолокація, розрахунок і оформлення доставки;
- `POST :4100/api/courier/orders/:id/accept | pickup | delivered` — дії курʼєра.

Помилки повертаються в єдиному форматі `{ "error": { "code", "message", "details" } }` з HTTP-кодами 400 (валідація), 401, 403, 404, 409 (конфлікт стану), 422 (порушення бізнес-правила), 402 (відмова банку). Повідомлення — українською, з полем, у якому помилка, щоб клієнт показав її під відповідним полем форми.

**Автентифікація та авторизація.** Паролі зберігаються як хеш bcrypt. Після входу клієнт отримує access-токен JWT [13] на 30 хв і випадковий refresh-токен на 30 днів, який у базі зберігається лише як SHA-256. Refresh-токен одноразовий: при оновленні видається нова пара, а повторне використання старого токена відкликає всі сесії користувача. Обидві системи перевіряють той самий підпис і issuer, тому вхід єдиний. Авторизація — на сервері: маршрутизатор перевіряє роль (RBAC), сервіси — належність ресурсу (клієнт бачить лише свої бронювання, замовлення й адреси, курʼєр — лише призначені йому доставки), автомати станів — право на конкретний перехід. Деактивований користувач втрачає доступ одразу, бо стан перевіряється в базі на кожному запиті. Додатково: helmet, CORS, обмеження частоти входу й реєстрації (20 запитів за хвилину), ліміти розміру тіла й файлів.

**Бізнес-процеси і стани.** Ключові процеси реалізовано як скінченні автомати (рис. 2.10, лістинг А.1). Для кожного переходу задано, хто може його виконати: власник ресурсу (OWNER), роль (STAFF, KITCHEN, ADMIN, COURIER) або лише сервер (SYSTEM). Сервер перевіряє, чи існує перехід (інакше 409 INVALID_TRANSITION), чи має актор право на нього (інакше 403 TRANSITION_FORBIDDEN) і чи виконано умови (лістинг А.2). Кожна зміна записується в журнал status_changes і розсилається в реальному часі.

!fig 2.10 | ../../diagrams/state-machines.png | Діаграма станів бронювання, замовлення в залі та доставки

Основні бізнес-правила:

- бронювання — лише в межах годин роботи, з кроком 30 хв, щонайменше за 30 хв і не далі ніж на 60 днів; 1–12 гостей; не більше трьох активних бронювань на клієнта;
- check-in — не раніше ніж за 60 хв до візиту, клієнт — лише скануванням QR-коду свого столика; завершити візит можна лише без неоплачених замовлень;
- замовлення в залі — лише після check-in; ціни беруться тільки з бази даних; страви зі стоп-листа не приймаються; офіціант не може «готувати», а кухар — «подавати»;
- оплата — лише поданого замовлення; рівно один успішний платіж на замовлення;
- доставка — лише в години роботи кухні мінус 45 хв, сума не менша за мінімальну для зони, не більше трьох активних доставок на клієнта; курʼєр — не більше двох замовлень, забрати можна лише готове;
- фонові задачі щохвилини скасовують непідтверджені бронювання, позначають no-show (через 20 хв), автоматично завершують оплачені візити та скасовують неоплачені онлайн-доставки (через 15 хв).

**Конкурентність і цілісність.** Створення бронювання виконується в транзакції з advisory lock PostgreSQL: перевірка вільності й вставка атомарні, а остання лінія захисту — EXCLUDE-обмеження. Зміни замовлень і дії курʼєрів виконуються з `SELECT … FOR UPDATE` на рядку замовлення, тож двоє курʼєрів не візьмуть одне замовлення, а дві дії кухні не перетруть одна одну. Оплата авторизується в шлюзі поза транзакцією (щоб не тримати блокування під час мережевої затримки), а фіналізується в транзакції з повторною перевіркою статусу.

### 2.5 Реалізація Web- та Mobile-застосунків та їх інтеграція

**Web-застосунок** написано на React 19 [5] з React Router 7 і Tailwind CSS. Дані з API завантажуються через TanStack Query [14]: кешування, повторні запити й автоматичне оновлення після подій реального часу. Кожна вкладка браузера має власну сесію (sessionStorage), тому в сусідніх вкладках можна одночасно працювати гостем, офіціантом і кухарем. Події Socket.IO інвалідують відповідні запити й показують сповіщення зі звуком: нове бронювання — бейдж у меню і toast, нове замовлення — тікет на kitchen display і в kanban (рис. 2.11). Сканер QR у Web працює через камеру браузера (getUserMedia і бібліотеку jsQR) або фото.

!fig 2.11 | fig/web-orders.jpg | Web: kanban замовлень офіціанта з позначкою «Доставка» для замовлень Delivery API

**Mobile-застосунок** — нативний застосунок на React Native з Expo SDK 57 [6], не WebView. Навігація — React Navigation 7 [15] із власним набором вкладок для кожної ролі. Застосунок працює з двома API через два HTTP-клієнти й два Socket.IO-зʼєднання; адреси обох систем визначаються автоматично або налаштовуються в профілі. Мобільні можливості: expo-camera (QR), expo-location (GPS і геокодер), expo-notifications (локальні сповіщення), expo-haptics (вібрація), expo-secure-store (токени).

**Двостороння інтеграція Web ↔ Mobile.** Обидва клієнти працюють з тими самими endpoint і тією самою базою даних, а сервер сповіщає зацікавлені сторони через кімнати Socket.IO: user:<id> — конкретний користувач, staff — зал, kitchen — кухня, couriers і dispatch — служба доставки.

Сценарій Mobile → Backend/API → Database → Web:

1. Гість у мобільному застосунку створює бронювання (`POST /api/reservations`).
2. Restaurant API перевіряє правила, записує бронювання зі статусом PENDING у таблицю reservations і надсилає подію reservation:created у кімнату staff.
3. У Web працівника залу без перезавантаження сторінки зʼявляється нове бронювання зі звуковим сигналом і бейджем.

Сценарій Web → Backend/API → Database → Mobile:

1. Працівник залу у Web натискає «Підтвердити» (`PATCH /api/reservations/:id/status`).
2. Сервер перевіряє роль і допустимість переходу, оновлює статус і журнал змін, надсилає подію reservation:updated у кімнату user:<id> гостя.
3. На телефоні гостя зʼявляється сповіщення «Бронювання підтверджено!», вібрація, статус на екрані змінюється сам.

Аналогічно проходить замовлення: гість замовляє з телефона → офіціант приймає у Web → кухар готує на kitchen display → гість бачить «Готується» і «Готово» з прогнозом часу → після оплати в Mobile офіціант отримує подію про оплату у Web. Для доставки ланцюжок проходить через дві системи: оплата в Delivery API → подія через PostgreSQL → тікет «Доставка» на kitchen display Restaurant API → «Готово» → подія назад у Delivery API → сповіщення курʼєру й клієнту.

### 2.6 Реалізація функціональності підвищеної складності

**Booking engine** (лістинг А.4). Вхід: дата, кількість гостей, бажана зона. Вихід: сітка слотів (час, доступність, кількість вільних столиків, завантаженість залу) і для кожного слоту — рекомендований столик з поясненням. Слоти генеруються від відкриття з кроком 30 хв; тривалість візиту залежить від кількості гостей (90–180 хв). Столик вважається вільним, якщо інтервал візиту, розширений на 15 хв буфера з кожного боку, не перетинається з активними бронюваннями. Серед вільних столиків обирається той, що має найменший штраф:

!eq (2.1) | score = 10·(місць − гостей) + 30·[інша зона] + 8·[бар без побажання] + Σ (90 − g)/5 − 5·[щільне прилягання]

де g — «мертвий» проміжок до сусіднього бронювання тривалістю від 0 до 90 хв. Штраф за фрагментацію не дає розкладу розпадатися на шматки по 30–60 хв, у які нікого не посадиш, тому за вечір вміщується більше гостей. Якщо слот зайнятий, сервер повертає найближчі вільні альтернативи.

**QR-коди.** QR-код бронювання (`smartrest://reservation/R-XXXXXX?t=<token>`) сканує хостес; QR-код столика (`smartrest://table/<qrToken>`) сканує гість. Токени випадкові (16–18 байт base64url); адміністратор друкує QR-картки й перевипускає QR-код столика, після чого старий перестає діяти. Сканування столика автоматично робить check-in за бронюванням саме на цей столик або пропонує walk-in.

**Sandbox payment** (лістинг А.5). Емуляція платіжного провайдера за зразком тестового режиму Stripe: перевірка номера картки алгоритмом Луна, терміну дії й CVC, визначення платіжної системи; детерміновані тестові картки для успіху, 3-D Secure, відмови банку й нестачі коштів; статуси платежу PENDING → REQUIRES_ACTION → SUCCEEDED / FAILED / REFUNDED. Повторний запит з тим самим заголовком Idempotency-Key повертає вже створений платіж, а частковий унікальний індекс гарантує одну успішну оплату. Повний номер картки не зберігається — лише платіжна система й останні чотири цифри.

**Kitchen display і прогноз готовності.** Кухар бачить колонки «Нові», «Готуються», «Готові до видачі» з таймерами й кольоровою індикацією запізнення. Перша відмічена страва переводить замовлення в «Готується», остання — у «Готово». Прогноз часу готовності враховує чергу кухні:

!eq (2.2) | ETA = now + Σ t_черги / N_станцій + max(t_страв)

де Σ t_черги — сумарний залишок часу приготування замовлень у черзі, N_станцій — кількість паралельних кухонних станцій, max(t_страв) — найдовший час приготування страви в замовленні.

**Рекомендації.** Гібридна пояснювана модель:

!eq (2.3) | score = 0,35·A + 0,25·P + 0,15·Pop + 0,10·R + 0,10·C + 0,05·T

де A — асоціативні правила «часто замовляють разом» (confidence і lift за історією замовлень), P — персоналізація за історією користувача, Pop — популярність, R — байєсівський рейтинг (один відгук 5★ не перемагає 40 відгуків 4,9★), C — доповнення кошика (напій до основної страви, десерт), T — час доби. Кожна рекомендація повертає причину, яку бачить гість.

**Real-time.** Socket.IO з автентифікацією JWT при підключенні; сервер розкладає сокети по кімнатах. Події між двома системами передаються через PostgreSQL LISTEN/NOTIFY (лістинг А.6): повідомлення, надіслане в транзакції, доставляється лише після COMMIT, тому подія ніколи не випереджає дані, а відкочена транзакція не надсилає нічого.

**Служба доставки як окрема система.** Delivery API — окремий процес і Docker-контейнер з власними маршрутами, Socket.IO, Swagger і фоновими задачами на спільній базі даних. Вартість доставки для зони:

!eq (2.4) | fee = 0, якщо subtotal ≥ freeFrom; інакше fee = zone.fee

де subtotal — сума страв, freeFrom — поріг безкоштовної доставки зони. Оформлення заборонене, якщо subtotal менша за мінімальну суму зони (minOrder); клієнт бачить, скільки бракує.

Прогноз доставки дорівнює прогнозу кухні з формули (2.2) плюс 5 хв на передачу курʼєру і час у дорозі для зони; після того як курʼєр забрав замовлення, прогноз рахується лише за дорогою.

**Геолокація** (лістинг А.7). Кожна зона має орієнтовний центр і радіус обслуговування. Мобільний застосунок отримує координати GPS, а Delivery API обчислює відстань до центрів зон за формулою гаверсинуса:

!eq (2.5) | d = 2R·arcsin √( sin²(Δφ/2) + cos φ₁·cos φ₂·sin²(Δλ/2) ),  R = 6371 км

Точка належить зоні, якщо d ≤ r; коли підходять кілька сусідніх зон, обирається та, для якої відношення d / r найменше. Відповідь містить зону, причину відмови (зона вимкнена або точка поза зонами), відстань від ресторану й оцінку часу в дорозі, а геокодер телефона підставляє вулицю й будинок.

**Аналітика.** Дашборд за 7, 14, 30 або 90 днів із порівнянням з попереднім періодом: виручка, середній чек, гості, бронювання, частка скасувань і no-show, середня оцінка, час приготування, виручка по днях, навантаження по годинах, топ страв, виручка за категоріями (рис. 2.12). У мобільному застосунку адміністратора є окремий блок доставки: кількість, частка у виручці, середній час до дверей, розподіл за зонами.

## РОЗДІЛ 3. ТЕСТУВАННЯ ТА АНАЛІЗ РЕЗУЛЬТАТІВ РОЗРОБКИ

### 3.1 Тестування програмної системи

**Методика.** Тестування виконано на кількох рівнях:

- **модульні тести** (Vitest) — booking engine, sandbox-шлюз, автомати станів, рекомендації, тарифи й години доставки, геолокація на контрольних даних;
- **інтеграційні тести API** (Vitest, Supertest, реальна PostgreSQL в окремій тестовій базі) — автентифікація, ролі, валідація, бізнес-правила, обмеження бази даних, повні цикли залу й доставки, події WebSocket і шини між системами;
- **наскрізні тести в браузері** (Playwright [16]) — сценарій захисту через інтерфейс Web і доставка через дві системи;
- **перевірка за днями тижня** — увесь набір тестів запускається 7 разів так, ніби сьогодні кожен день тижня, бо графік роботи ресторану й доставки різний для буднів і вихідних;
- **статичний аналіз** — TypeScript у строгому режимі, ESLint і Prettier;
- **ручна перевірка Mobile** — сценарії гостя, курʼєра і персоналу в Expo Go та у web-превʼю з емуляцією камери й геолокації.

Час у тестах підміняється, тому сценарії детерміновані незалежно від моменту запуску. Усі перевірки автоматично виконуються в GitHub Actions на кожен push: lint, тести backend для всіх днів тижня, збирання Web і Mobile та наскрізні тести на PostgreSQL. ### 3.2 Представлення та аналіз результатів роботи системи

Роботу завершеної системи продемонстровано на наскрізних сценаріях, які повторюють захист.

**Сценарій 1: повний цикл у залі.** Новий користувач реєструється в мобільному застосунку, обирає час і бачить план залу з рекомендованим столиком (рис. 2.6, б). Restaurant API створює бронювання PENDING у таблиці reservations, і працівник залу без перезавантаження бачить його у Web. Після підтвердження гість отримує сповіщення на телефоні. Прийшовши, гість сканує QR-код столика (рис. 2.6, в) — бронювання переходить у CHECKED_IN, а столик на живому плані залу у Web стає зайнятим (рис. 2.4). Гість замовляє з телефона, офіціант приймає замовлення в kanban, кухар готує його на kitchen display (рис. 2.5), а гість бачить зміну статусів і прогноз часу (рис. 2.7, б). Після подачі гість платить карткою з 3-D Secure (рис. 2.7, в): в одній транзакції створюється платіж SUCCEEDED і замовлення стає PAID, офіціант отримує подію про оплату у Web. Насамкінець гість залишає відгук, і візит завершується.

**Сценарій 2: доставка через дві системи.** Клієнт у мобільному застосунку натискає «Моє місцезнаходження» — Delivery API визначає район і показує тариф і прогноз (рис. 2.8, а, б). Після оплати замовлення типу DELIVERY записується в спільну таблицю orders, а подія через PostgreSQL потрапляє в Restaurant API — на kitchen display у Web зʼявляється тікет «Доставка» з районом (рис. 2.5). Курʼєр бере замовлення в черзі (рис. 2.9, а), після «Готово» забирає його — клієнт бачить «Курʼєр уже в дорозі» з часом прибуття (рис. 2.8, в) — і вручає. Аналітика ресторану автоматично враховує виручку обох каналів (рис. 2.12).

**Сценарій 3: ролі та заборонені операції.** Клієнт намагається підтвердити своє бронювання або відкрити чуже замовлення — сервер повертає 403; офіціант не може перевести замовлення в «Готується»; курʼєр не може забрати замовлення до «Готово»; неправильні дані (пароль «123», телефон із пʼяти цифр, бронювання на 08:00) відхиляються з поясненням під полем.

**Аналіз результатів.** Реалізовано всю функціональність, погоджену в матриці функціональності (табл. 1.2): CORE повністю, ADVANCED (booking engine, QR, sandbox payment) і BONUS (kitchen display, рекомендації, real-time, служба доставки з геолокацією, аналітика, Docker, CI, автоматизовані тести). Web і Mobile працюють з єдиними даними через API, бізнес-процеси мають стани й правила переходів, які перевіряє сервер, а цілісність даних гарантована на рівні бази даних. Система працює не лише на демо-даних: адміністратор може створити нову страву, столик, зону доставки чи курʼєра, і новий клієнт одразу проходить з ними повний цикл.

Обмеження: платіжний шлюз емульований (sandbox) і не списує реальні кошти; сповіщення на телефоні — локальні, без сервера push-повідомлень; межі зон доставки задані наближено колами; мобільний застосунок запускається через Expo Go без публікації в магазинах застосунків.

## ВИСНОВКИ

У курсовій роботі поставлено завдання автоматизувати повний бізнес-процес ресторану — від бронювання до оплати — та створити власну службу доставки, обʼєднавши гостей, персонал залу, кухню й курʼєрів в одну систему реального часу.

Проведено аналіз предметної області та чотирьох аналогів (OpenTable, Choice QR, Poster POS, Glovo) і показано, що жоден із них не покриває повний цикл обслуговування разом із власною доставкою. Визначено пʼять ролей, сформовано функціональні вимоги для кожної ролі й нефункціональні вимоги, побудовано діаграми варіантів використання та специфікації ключових варіантів використання.

Розроблено систему SMART RESTAURANT, яка складається з Web-застосунку на React, нативного мобільного застосунку на React Native (Expo), двох серверних систем — Restaurant API і Delivery API на Node.js і Express — та єдиної бази даних PostgreSQL із 14 таблиць. Клієнти працюють з даними лише через API; обидві системи приймають єдиний обліковий запис і обмінюються подіями через PostgreSQL LISTEN/NOTIFY.

Реалізовано Web-функції гостя, працівника залу, kitchen display і адміністрування; мобільні функції гостя (бронювання, QR check-in камерою, замовлення, оплата, доставка з геолокацією), курʼєра і персоналу; серверну автентифікацію з JWT і ротацією refresh-токенів, RBAC, валідацію, автомати станів бронювання, замовлення та доставки з перевіркою прав і умов переходів. Реалізовано компоненти підвищеної складності: booking engine зі штрафною функцією та гарантією від перетинів у базі даних, QR-коди бронювань і столиків, sandbox-оплату з 3-D Secure, ідемпотентністю та поверненням коштів, kitchen display з прогнозом готовності, пояснювані рекомендації, real-time на Web і Mobile, службу доставки як окрему систему з геолокацією.

Мету роботи досягнуто: гість бронює, замовляє й платить зі смартфона, персонал бачить зал і кухню в реальному часі, а доставка проходить від оформлення до вручення без стороннього агрегатора. Тестування підтвердило коректність роботи: 118 автоматизованих тестів API для кожного дня тижня, наскрізні тести в браузері та безперервна інтеграція проходять без помилок.

Подальший розвиток системи: підключення реального платіжного провайдера, серверні push-сповіщення, точні межі зон доставки за полігонами районів, оптимізація маршрутів курʼєрів і публікація мобільного застосунку в магазинах застосунків.
