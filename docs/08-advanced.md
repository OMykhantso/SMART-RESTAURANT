# 8. Компоненти підвищеної складності

## 8.1 Booking engine (ADVANCED)

Код: `backend/src/modules/booking/engine.ts` (чисті функції, покриті юніт-тестами) та `booking.service.ts`.

**Вхід:** дата, кількість гостей, бажана зона. **Вихід:** сітка слотів (час, доступність, скільки столиків лишилось, завантаженість залу 0..1) і для кожного слоту — рекомендований столик з поясненням.

1. **Генерація слотів.** Від відкриття з кроком 30 хв, поки `start + тривалість ≤ закриття`; відкидаються слоти раніше за `now + 30 хв` (для клієнта). Тривалість: ≤2 гостей — 90 хв, ≤4 — 120, ≤6 — 150, більше — 180.
2. **Перевірка конфліктів.** Інтервал `[start − 15 хв, end + 15 хв)` не повинен перетинатися з жодним активним бронюванням столика (буфер — прибирання й сервіровка).
3. **Вибір столика (best-fit).** Для кожного вільного столика з достатньою кількістю місць рахується штрафна функція (менше — краще):

```
score = 10 · (місць − гостей)                    — не «марнуємо» великі столи
      + 30 · [зона ≠ бажана]                     — повага до вибору гостя
      +  8 · [барне місце, якщо зону не обрано]  — бар лише за бажанням
      + Σ (90 − g) / 5  для «мертвих» проміжків 0 < g < 90 хв до/після сусідніх бронювань
      −  5 · [щільне прилягання до сусіднього бронювання]
```
   Штраф за фрагментацію — ключова ідея: алгоритм уникає розкладів, де між гостями лишаються «шматочки» по 30–60 хв, у які нікого не посадиш. Так більше гостей вміщується за вечір.
4. **Альтернативи.** Якщо слот зайнятий — сервер повертає найближчі вільні слоти (сортування за |Δt|).
5. **Гарантія.** Критична секція (`pg_advisory_xact_lock`) + EXCLUDE-обмеження PostgreSQL.

**Приклад (юніт-тест):** столик A звільняється о 11:45 (+15 = 12:00), столик B — о 11:00. Для бронювання 12:00–14:00 обирається A: у B лишився б «мертвий» проміжок 45 хв (штраф 9), а A прилягає щільно (−5).

## 8.2 QR-коди (ADVANCED)

| QR | Формат | Хто сканує | Що відбувається |
|---|---|---|---|
| Бронювання | `smartrest://reservation/R-XXXXXX?t=<token>` | хостес (Web: камера / фото / ручний код) | check-in з перевіркою підпису `t`, статусу та вікна часу |
| Столик | `smartrest://table/<qrToken>` | гість (Mobile, камера) | автоматичний check-in за бронюванням **саме на цей столик** або пропозиція walk-in |

* Токени випадкові (16–18 байт base64url), QR столика перевипускається адміністратором (старий перестає діяти); друк QR — з адмін-панелі.
* Web-сканер: `getUserMedia` + декодування кадрів `jsQR` у canvas; запасний варіант — фото. Mobile — `expo-camera` з `barcodeScannerSettings`.

## 8.3 Sandbox payment (ADVANCED)

Код: `backend/src/modules/payments/sandbox.ts`, `payments.service.ts`. Емуляція провайдера за зразком Stripe test mode:

* валідація картки: **алгоритм Луна**, місяць/рік (картка дійсна до кінця місяця), CVC (3/4 цифри), визначення Visa/Mastercard за BIN;
* детерміновані тестові картки: `4242…4242` — успіх, `4000…3220` — **3-D Secure** (код `123456`), `4000…0002` — відмова банку, `4000…9995` — недостатньо коштів;
* статуси платежу `PENDING → REQUIRES_ACTION → SUCCEEDED / FAILED`, код і текст відмови, `pi_sbx_…` референс;
* **ідемпотентність** (`Idempotency-Key`), блокування рядка замовлення, одна успішна оплата на замовлення;
* **чайові** 0/5/10/15 %, оплата готівкою через офіціанта, чек;
* повний номер картки **не зберігається** — лише бренд і останні 4 цифри.

## 8.4 Kitchen display (BONUS)

Екран `/kitchen`: колонки «Нові / Готуються / Готові до видачі», великі тікети з номером столу, таймер від прийняття, норма часу (найдовша страва), прогрес-бар і кольорова індикація запізнення (жовтий ≥ 70 %, червоний ≥ 100 %). Кухар відмічає окремі страви — перша відмітка автоматично переводить замовлення в «Готується», остання — у «Готово». Звук про нові замовлення (Web Audio API), стоп-лист, повноекранний режим.

## 8.5 Рекомендації (BONUS)

Код: `backend/src/modules/recommendations/engine.ts`. Гібридна пояснювана модель:

```
score(d) = 0.35·A + 0.25·P + 0.15·Pop + 0.10·R + 0.10·C + 0.05·T
```

| Фактор | Як рахується |
|---|---|
| **A** — «часто замовляють разом» | асоціативні правила за історією замовлень: `confidence(c→d) = P(d|c)`, підсилена `lift = confidence / P(d)`; мінімальна підтримка — 2 спільні замовлення |
| **P** — персоналізація | 0.6 · частота замовлень страви користувачем + 0.4 · прихильність до категорії |
| **Pop** — популярність | `log(1+n) / log(1+max)` |
| **R** — рейтинг | байєсівське згладжування `(C·m + Σr)/(C + n)`, C = 5: один відгук 5★ не перемагає 40 відгуків 4.9★ |
| **C** — доповнення кошика | основна страва без напою → напої; без десерту → десерти; не пропонувати третій суп |
| **T** — час доби | сніданки до 12:00, коктейлі після 17:00, супи в обід |

Кожна рекомендація повертає **причини** («Часто замовляють разом із «Стейк рібай»», «Ви часто це замовляєте», «Завершіть вечерю десертом») і внесок факторів — це видно в меню, картці страви та кошику.

**Контрольні дані (юніт-тести):** у 8 з 9 замовлень зі стейком є вино → до кошика зі стейком першим рекомендується вино (confidence 0.89, lift > 1); до піци — лимонад; страви з кошика і стоп-листа не рекомендуються; улюблена страва користувача піднімається вгору.

## 8.6 Прогноз часу готовності (ETA)

```
ETA = now + (Σ залишку приготування замовлень у черзі) / N_станцій + max(prep_time страв замовлення)
```
Для замовлення, що вже готується: `preparing_at + max(prep_time)`. Прогноз оновлюється при прийнятті та початку приготування, показується клієнту кільцевим таймером.

## 8.7 Real-time (BONUS)

Socket.IO з JWT-автентифікацією при підключенні; сервер розкладає сокети по кімнатах (`user:<id>`, `staff`, `kitchen`, `public`). Web інвалідовує кеш TanStack Query і показує toast зі звуком; Mobile — банер, вібрацію та локальне сповіщення («Ваше замовлення готове! 🍽»).
